## 1. Задача

Нужно спроектировать систему для сбора данных с датчиков. Датчики отправляют измерения постоянно, при этом сообщения могут приходить с задержкой, повторяться или поступать не по порядку.

Система должна решать две задачи: быстро показывать текущие показатели и формировать суточные отчёты. При расчётах важно не учитывать одно событие дважды и не терять поздно пришедшие данные.

Для примера рассматривается сеть из 100 датчиков, каждый из которых отправляет одно измерение в секунду. Получается около 8,64 млн сообщений в сутки. Если одно сообщение занимает примерно 200 байт, объём исходных данных составит около 1,73 ГБ в сутки без учёта служебной информации.

## 2. Источники данных

Основной источник — IoT-датчики, которые передают температуру и другие показатели оборудования. Для каждого измерения предусмотрены:

- `event_id` — уникальный идентификатор события;
- `device_id` — идентификатор датчика;
- `event_time` — время измерения;
- `value` — измеренное значение.

Пример сообщения:

```json
{"event_id":"evt-000001","device_id":"sensor-17","event_time":"2026-11-18T12:00:00Z","value":23.4}
```

Сначала сообщения попадают в шлюз приёма, где проверяется их формат. Затем они отправляются в Kafka. Это позволяет хранить поток событий и повторно прочитать сообщения, если обработчик временно недоступен.

## 3. Выбранная архитектура

Для решения выбрана **Kappa-архитектура**. Основой системы служит единый поток исходных событий. Данные сохраняются, поэтому при необходимости их можно обработать повторно.

Основные компоненты:

1. **IoT-датчики и шлюз** — отправляют и проверяют измерения.
2. **Apache Kafka** — принимает события и хранит их в журнале.
3. **Apache Flink** — обрабатывает поток и рассчитывает оперативные показатели.
4. **PostgreSQL** — хранит результаты, которые нужны для просмотра и отчётов.
5. **Архив исходных событий** — нужен для длительного хранения и повторных расчётов.
6. **Суточный пересчёт** — формирует итоговые показатели за день из сохранённых данных.

### Почему Kappa

Можно было использовать Lambda-архитектуру с двумя отдельными путями обработки: потоковым и пакетным. Но в таком случае пришлось бы поддерживать две реализации расчётов. В выбранном варианте основой остаётся один журнал событий, а суточный расчёт использует сохранённые исходные данные и те же правила обработки.

### Работа с задержками и повторами

Для определения суток используется `event_time`, то есть время самого измерения, а не момент получения сообщения.

В потоковой обработке можно настроить **watermark**, например на 10 минут. Это позволяет учитывать события, пришедшие с небольшой задержкой. События, опоздавшие сильнее, сохраняются в архиве и учитываются при повторном расчёте суточного отчёта.

Повторы определяются по `event_id`. Если сообщение с таким идентификатором уже обработано, повторно учитывать его не нужно. На уровне PostgreSQL это можно дополнительно контролировать уникальным ключом и командой `ON CONFLICT DO NOTHING`.

Для восстановления после сбоя предполагаются повторное чтение Kafka и контрольные точки Flink. При этом отсутствие потерь и повторов во всей системе требует правильной настройки каждого компонента — одной Kafka для этого недостаточно.

## 4. Docker

В файле `docker-compose.yml` подготовлен небольшой стенд для хранения и просмотра данных:

| Сервис | Назначение | Порт |
|---|---|---|
| PostgreSQL 16 | База данных | 5432 |
| Adminer | Веб-интерфейс для работы с БД | 8080 |

Kafka, Flink и архив показаны на архитектурной схеме, но в этот упрощённый Docker Compose не включены.

Для запуска в папке с файлом `docker-compose.yml`:

```bash
docker compose up -d
docker compose ps
```

После запуска Adminer должен быть доступен по адресу `http://localhost:8080`.

Параметры подключения:

- Система: PostgreSQL
- Сервер: `postgres`
- Пользователь: `sport`
- Пароль: `sportpass`
- База данных: `telemetry`

Для проверки хранения событий можно создать таблицу:

```sql
CREATE TABLE IF NOT EXISTS raw_events (
    event_id TEXT PRIMARY KEY,
    device_id TEXT NOT NULL,
    event_time TIMESTAMPTZ NOT NULL,
    value DOUBLE PRECISION NOT NULL
);
```

И добавить тестовое событие:

```sql
INSERT INTO raw_events (event_id, device_id, event_time, value)
VALUES ('evt-000001', 'sensor-17', '2026-11-18T12:00:00Z', 23.4)
ON CONFLICT (event_id) DO NOTHING;

SELECT * FROM raw_events;
```

Если выполнить `INSERT` с тем же `event_id` ещё раз, вторая строка не добавится. Это простой пример защиты от дублирования на уровне базы данных.

**Результат запуска:** конфигурация подготовлена; фактический запуск контейнеров и вывод `docker compose ps` пока не проверены. Перед сдачей нужно выполнить команды на своём компьютере и приложить реальный результат проверки.

Остановка сервисов:

```bash
docker compose down
```

## 5. Путь данных

1. Датчик создаёт измерение и присваивает ему `event_id` и `event_time`.
2. Шлюз проверяет сообщение и отправляет его в Kafka.
3. Flink читает сообщения, учитывает время события и отбрасывает дубли.
4. Результаты обработки записываются в PostgreSQL для мониторинга.
5. Исходные события дополнительно сохраняются в архив.
6. После окончания суток из архива выполняется пересчёт с учётом поздних событий.
7. Полученный суточный отчёт сохраняется в PostgreSQL.

Таким образом, оперативные показатели появляются быстро, а итоговые отчёты можно уточнять, если часть событий пришла позже.

## 6. Вывод

В работе я спроектировал архитектуру обработки событий от датчиков. Для этой задачи выбрал Kappa-подход, потому что он позволяет использовать сохранённый поток событий для повторной обработки и не поддерживать две независимые схемы расчётов.

Основные проблемы такой системы — задержка сообщений, дубли и возможные сбои. Для их решения предусмотрены обработка по `event_time`, дедупликация по `event_id`, хранение исходных событий и повторный суточный расчёт.

Также подготовил Docker Compose с PostgreSQL и Adminer. Он подходит для проверки хранения данных, но не заменяет полноценный потоковый стенд с Kafka и Flink.
